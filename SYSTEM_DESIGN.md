# System Design

---

## Functional Requirements (User Facing)

- **FR1**: `/start` -> Bot introduces itself and shows available commands.
- **FR2**: `/enter_url <youtube url>` -> User submits a YT podcast URL. System sends an immediate acknowledgement, validates the URL, and in the background fetches the transcript, confirms readiness. User is now in an active session tied to that video (per user rate limiting - 10 videos per day). Daily video ingestion count per user is tracked in Postgres, reset at midnight UTC.
- **FR3**: `/ask <question>` -> User asks a question. System retrieves relevant transcript chunks, calls Groq, returns a grounded answer. Session memory of prior QnA is maintained within the session.
- **FR4**: `/get_notes` -> System generates structured notes (500-5000 words, sectioned). Per-video global limit: 2 generations (prevents the same popular video from being summarized 100 times, burning your Groq credits) Notes are permanently stored in Postgres tagged with the model version. When the system upgrades to a new model, existing cached notes are invalidated and regenerated on next request - on next /get_notes request, if stored notes were generated by an older model version, regenerate them (counts as an LLM call against the rate limit).
- **FR5**: `/history` -> User can see their QnA history for the current session (fetched instantly from cache).
- **FR6**: `/clear` -> User clears their session, allowing them to enter a new URL and enter a new session. 
- **FR7**: `/help` -> Shows all commands with description.
- **FR8**: If `/ask` or `/get_notes` is called without a prior `/enter_url`, bot sends a warning: "Please enter a podcast URL first using `/enter_url`" and does not proceed - it does NOT clear any existing session. The user needs to manually restart the session using `/enter_url`.
- **FR9**: If the YouTube URL is invalid or has no transcript available, inform the user with a specific error ("This video has no subtitles/transcript available").
- **FR10**: If /get_notes is called and the rate limit (2 per video) is exhausted, inform the user: "Notes have been generated 2 times for this video. Use /ask to query it directly."

## Non-Functional Requirements

**Availability**:
- **NFR1**: The system targets best-effort availability on a single instance. No redundancy or failover is required at current stage. Planned maintenance may cause brief downtime.

**Concurrency/Throughput**:
- **NFR2**: The system should handle 50 users active within any 60-second window, with no more than ~10 genuinely simultaneous Groq API calls in flight, without degradation at current stage - this sets Redis connection pool size, Groq API rate limit planning etc.

**Scalability**: 
- **NFR3**: Should be easily horizontally scaled -> from single CPU to multi-Cpu or a distributed system easily, in future. In future, we will make knowledge graphs of the truncated chunks as well.

**Latency/Performance**:
- **NFR4**: `/enter_url` processing (transcript fetch + embed) should complete within 30 seconds for videos upto 3 hours. User gets a "⌛Processing..." acknowledgement immediately, result when done (async response pattern).
- **NFR5**: `/ask` should return an answer within 5-10 seconds (mostly Groq API latency, ~1-3s for fast models like Llama 3 8B).
- **NFR6**: `/get_notes` should complete within 60 seconds (upper end) for a full podcast.

**Reliability**:
- **NFR7**: If Groq API is down, the system should not show a raw 500 error, but show "The LLM service is temporarily unavailable, please try again in a few minutes".
- **NFR8**: If Redis goes down, all the active sessions are lost. Users will be prompted to re-enter their URL. Postgres remains the source of truth for rate limits and notes.

**Consistency**:
- **NFR9**: Rate limit (2 notes per video) must be consistent. Two users hitting `/get_notes` on the same video simultaneously should not both get through if the count is already at 2. This requires atomic Redis operations (INCR + expiry), not a read-then-write pattern.
- **NFR10**: Store chunk text as Qdrant payload. Then Redis only holds sessions and Q&A history, not the chunks themselves.
- **NFR11**: If a user's session has expired (Redis TTL elapsed), the bot informs: "Your session has expired. Please re-enter the URL with `/enter_url` to continue." The video's embeddings in Qdrant may still exist, so re-ingestion checks Qdrant first before re-fetching the transcript. Same with the notes, they'll be stored on postgres.

**Security**:
- **NFR12**: User question input is capped at 500 characters. Questions are passed to the LLM inside a structured prompt template. No user input is executed as code or system commands.
- **NFR13**: API keys (Groq, Telegram Bot Token) must never appear in code or logs.

**Observability**: 
- **NFR14**: Every command invocation, its latency, success/failure status and hashed user_id must be logged in stuctured format.
- **NFR15**: Key metrics must be exposed: request count by command, p95 latency per command, cache hit rate, Groq API error rate.

**Extensability**:
- **NFR16**: The transcript ingestion component must be swappable (today: YouTube subtitles, future: Whisper on audio file, future: Spotify API). This means ingestion must be behind an interface, not hardcoded.
- **NFR17**: Language detection and multilingual response must be pluggable without redesigning the core pipeline.

## Constraints and Assumptions

- **C1**: We assume API usage and we are NOT self-hosting.
- **C2**: Single YouTube URL per session, no playlist support.
- **C3**: Single CPU at current stage. Uvicorn runs one process. Parallelism is achieved through async I/O, not multi-processing.
- **C4**: No GPU available at current stage, which motivated C1.
- **C5**: Telegram as the only supported client interface - the system is designed around Telgram's Bot API and webhook model.
- **C6**: YouTube is the primary source of transcripts, but if unavailable, it'll fall back to `faster-whisper` model (locally).
- **C7**: No offline fallback exists for the LLM.
- **C8**: All infrastructure runs on a single machine (single Docker host). `docker-compose` is the deployment unit at current stage, not Kubernetes. K8s manifests will be provided for future horizontal scaling (NFR3) but are not the active deployment method.

## Capacity Estimation

**Assumptions for estimation:**
- Daily active users: 100
- Average videos per user per day: 2
- Average questions per day: 5
- Average notes generation per video: 1.5 (some videos hit the limit)
- Average podcast transcript length: 15,000 words ~ 20,000 tokens ~ 80 KB (4 bytes per token)

1. **Storage  (Redis):**
- Per video session:
    - QnA history per session = ~5KB (per question) * 5 = ~25KB
    *(each Q = ~500 char max;*
    *each A = ~1000 char ~1000 tokens (1 token is approx 4 char) ~4000 char*
    *Each QnA pair ~4500 char (1 char ~ 1 byte) = ~4.5KB)*
    - Session metadata (video_id, user_id, state): ~1KB
- Raw total per active session = ~26KB
- Additional = *50–90 bytes for internal pointers, metadata, and expiration tracking* + *~16 bytes for redisObject*
- Active sessions at peak (say 20 concurrent users, each on 1 video): 20 * ~27KB = ~540KB
- With 2-hour TTL, even with 100 users all ingesting 2 videos, total Redis footprint is: 200 videos * ~27KB = ~5.4MB
*Completely trivial. Redis is fine.*

2. **Groq API calls:**
- Per question: ~2800 tokens input + ~400 tokens output = ~3200 tokens total.
    - ~2000–2500 tokens (chunks) + ~300 tokens (system prompt + history + question) = ~2500–2800 tokens input.
    - Output is ~300-500 tokens.
- Per notes generation: 
    - 1 API call per chunk batch;
    - ~10 batches for a 3-hour podcast = ~10 API calls × ~3000 tokens each = ~30,000 tokens per notes run.
- Daily: 100 users × 5 questions = 500 Q calls + 100 users × 1.5 notes = 150 notes runs × 10 calls = 1500 calls
- Total daily Groq calls: ~2000 calls, ~5M tokens — well within Groq's free tier limits.

3. **Qdrant:**
- 100 users × 2 videos = 200 videos/day
- `all-MiniLM-L6-v2` sentence-transformer -> produces 384-dim vectors (512 is the upper limit for now):
    - ~300 chunks * 384 dims * 4 bytes = ~461KB per podcast.
- At 461KB each: 
    - 30 days = 461KB * 2 videos per day * 30 days =  ~2.7GB;
    - 90 days = ~2.7GB * 3 = ~8GB 
*still trivial on any modern day machine*.

```sql
CREATE TABLE ingested_videos (
    video_id        VARCHAR(20) PRIMARY KEY,
    url             TEXT NOT NULL,
    title           TEXT,
    duration_secs   INTEGER,

    transcript_hash VARCHAR(64),
    chunk_count     INTEGER,
    status          VARCHAR(20),
    ingested_at     TIMESTAMPTZ DEFAULT NOW(),

```

```sql
CREATE TABLE notes_generation_log (
    id              SERIAL PRIMARY KEY,
    video_id        VARCHAR(20) REFERENCES ingested_videos(video_id),
    user_hash       VARCHAR(64),     --hashed telegram user_id
    notes_content   TEXT,
    model_version   VARCHAR(50) NOT NULL,
    generated_at    TIMESTAMPTZ DEFAULT NOW()
);
```

```sql
CREATE TABLE request_logs (
    id              BIGSERIAL PRIMARY KEY,
    request_id      UUID DEFAULT gen_random_uuid(),
    user_hash       VARCHAR(64),
    command         VARCHAR(30),      --/ask, /get_notes, /enter_url
    video_id        VARCHAR(20),
    success         BOOLEAN,
    latency_ms      INTEGER,
    error_type      VARCHAR(50),
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

## Flow 1: `/enter_url` — The Ingestion Pipeline
```
User sends: /enter_url https://a_youtube_video_url

Telegrm Bot:
    1. Parse command, extract URL
    2. Send immediate acknowledgement: "⏳ Processing..."
    3. POST /api/v1/ingest { video_url, user_id }

FastAPI /ingest:
    4. Extract video_id from URL (parse query params)
    5. Check daily per-user video ingestion count (FR2 — 10 videos/day, tracked in Postgres, reset at midnight UTC).
    6. Check Qdrant: does collection video_id exist with vectors?
        YES -> skip ingestion, go to step 11
    7. Check Postgres: does ingested_videos WHERE video_id = ? exist AND status = 'ready'?
        YES -> re-warm Redis from stored data, go to step 11
    8. yt-dlp fetches transcript. If fails -> fall back to faster-whisper, return "Taking a little longer. Please hold up..."
    9. Chunking: split chunks into 512/384-token chunks and 64-token overlap
    10. Embedding: encode chunks via sentence-transformers
        -> Store vectors in Qdrant (collection named by video_id)
        -> Store raw transcript in Redis: session:{user_id}:transcript (TTL 2hr)
        -> Write to Postgres: ingested_videos (status='ready')
    11. Set Redis: session:{user_id}:video_id = video_id
    12. Return: { status: "ready", title: "..." }

Telegram Bot:
    13. Send: "Your video is ready! Ask questions with /ask or get notes with /get_notes"
```
**Key design decision:** steps 8-10 are I/O bound (network + computation). These run as a FastAPI `BackgroundTask` so the HTTP response returns immediately (step 12 returns "processing"), and the bot polls or uses a callback pattern to notify when done. This prevents Telegram's webhook from timing out.

## Flow 2: `/ask` — The RAG Query Pipeline
```
User sends: /ask What did the guest say about transformers?

Telegram Bot:
    1. Check session: GET /api/v1/session/{user_id}/history (to confirm active session)
    2. If no active session: "Please enter a URL first with /enter_url"
    3. POST /api/v1/query { video_id, user_id, question }

FastAPI /query:
    4. Retrieve video_id from Redis: session:{user_id}:video_id
    5. Embed the question using same embedding model
    6. Qdrant semantic search: top-5 chunks from collection video_id
    7. Retrieve Q&A history from Redis: session:{user_id}:history (last 3 pairs for context)
    8. Build prompt:
        SYSTEM: You are a podcast analysis assistant. Answer ONLY from the transcript context provided.
        CONTEXT: <5 retrieved chunks>
        CONVERSATION HISTORY: <last 3 Q&A pairs>
        USER QUESTION: <question>
    9. Call Groq API (async HTTP call, non-blocking)
    10. Parse response
    11. Append {question, answer, timestamp} to Redis: session:{user_id}:history
    12. Log to Postgres: request_logs
    13. Return: { answer, source_chunks, latency_ms }

Telegram Bot:
    14. Send answer to user
    15. Append "(Sources: chunk 2, 7, 12)" if you want citation support
```

## Flow 3: `/get_notes` — Rate Limited Notes Generation
```
FastAPI /notes:
    1. Check Postgres: 
        SELECT COUNT(*) FROM notes_generation_log 
        WHERE video_id = ? 
        AND model_version = <current_model_version>
    => If count >= 2 -> rate limit hit for this model version
    => If count < 2 -> allow generation
    2. Check if notes exist in Postgres AND what model version generated them. If the stored model version != current model version -> delete/invalidate the existing notes and regenerate (counts against rate limit).
    3. Check Redis: video:{video_id}:notes exists?
        YES -> return cached notes (cache hit, no LLM call!)
    4. Retrieve all chunks from Qdrant (scroll through all vectors in the collection and get their payload text).
    5. Map-reduce notes generation:
        a. Split chunks into batches of 10
        b. For each batch: call Groq to generate a section summary (async, concurrent)
        c. Combine section summaries: call Groq once more to synthesize final structured notes
    6. Store in Redis: video:{video_id}:notes (TTL 2hr, replaces previous)
    7. INSERT INTO notes_generation_log (video_id, user_hash, model_version, generated_at)
    8. Return notes + word_count + generation_count
```
The map-reduce pattern in step 4 is important. A 3-hour podcast has 300+ chunks. You can't fit all of them in one LLM context window. So you summarize in batches (map), then synthesize the summaries (reduce). This is called **hierarchical summarization** and is standard practice.

## Full Tech Stack Decision

| Layer | Tool | Why |
|---|---|---|
| Bot framework | `aiogram` 3.x | Best async Telegram library, clean handler design |
| API framework | FastAPI + Uvicorn | Async, fast, auto-docs |
| Task queue | ARQ (async) or Celery | Long-running ingestion jobs |
| Vector DB | Qdrant | Already in your stack, good Docker support |
| Cache + session | Redis | TTL support, atomic ops for rate limiting |
| Persistent DB | Postgres | Rate limit source of truth, request logs |
| LLM | Groq API (Llama 3 8B) | Fast, cheap, great for RAG |
| Embeddings | sentence-transformers | Local, no API dependency |
| Transcript fetch | yt-dlp | Already in your stack |
| Experiment tracking | MLflow | Log chunking/embedding experiments |
| Observability | structlog + prometheus-fastapi-instrumentator | Structured logs + metrics |
| Visualization | Grafana | Metrics dashboards |
| Containerization | Docker + docker-compose | Dev environment |
| Orchestration | k3s / k8s manifests | Portfolio demonstration |
| CI/CD | GitHub Actions | Lint + test + deploy |
| Config | Pydantic BaseSettings | 12-factor app config |
